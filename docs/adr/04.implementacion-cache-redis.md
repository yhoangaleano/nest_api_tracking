# ADR 004: Implementación de caché de lectura con Redis

**Estado:** Aceptado
**Fecha:** 2025-11-18

## 1. Contexto

Con la adopción de PostgreSQL (ADR 003), la consulta principal del sistema, `GET /api/v1/tracking/:trackingId`, implica una operación de `JOIN` entre la tabla `units` y la tabla `checkpoints`. Aunque esta operación es eficiente con una indexación adecuada, puede generar una carga significativa en la base de datos a medida que el volumen de datos crece, especialmente si muchos usuarios consultan el mismo tracking repetidamente.

Para garantizar una alta disponibilidad y un bajo tiempo de respuesta en las lecturas, es necesario un mecanismo que alivie la carga sobre la base de datos principal.

## 2. Decisión

Se implementará una capa de caché de lectura utilizando **Redis** para el endpoint `GET /api/v1/tracking/:trackingId`.

El flujo de consulta será el siguiente:
1.  Cuando se recibe una petición para un `trackingId`, el sistema primero intentará buscar el resultado en la caché de Redis usando una clave única (ej. `tracking:T-ABC-123`).
2.  **Cache Hit (Dato encontrado):** Si el dato existe en Redis, se devuelve directamente al cliente, evitando por completo la consulta a PostgreSQL.
3.  **Cache Miss (Dato no encontrado):** Si el dato no está en Redis, se realiza la consulta a PostgreSQL. El resultado obtenido se almacena en Redis con un **TTL (Time-To-Live)** definido (ej. 1 hora) y luego se devuelve al cliente.

### Estrategia de invalidación

Para evitar que los usuarios vean datos obsoletos, es crucial invalidar la caché cuando los datos cambian. La estrategia será:
*   **Invalidación explícita:** Después de que un nuevo checkpoint se registre exitosamente para un `trackingId` (en la operación `POST /api/v1/checkpoints`), el sistema eliminará explícitamente la clave correspondiente de Redis (ej. `DEL tracking:T-ABC-123`).

De esta manera, la próxima vez que se consulte ese `trackingId`, ocurrirá un `Cache Miss` forzado, y los datos frescos se recuperarán de PostgreSQL y se volverán a cachear.

## 3. Consecuencias

### Positivas (+)

*   **Reducción drástica de la carga en la base de datos:** La mayoría de las consultas de lectura serán servidas por Redis, que es una base de datos en memoria extremadamente rápida. Esto libera a PostgreSQL para que se concentre en las operaciones de escritura.
*   **Menor latencia para el usuario final:** Las respuestas desde la caché son casi instantáneas (sub-milisegundos), mejorando significativamente la experiencia del usuario.
*   **Mayor escalabilidad y resiliencia:** El sistema puede manejar un volumen mucho mayor de consultas de lectura. Si la base de datos experimenta una lentitud temporal, las lecturas cacheadas no se verán afectadas.

### Negativas (-)

*   **Mayor complejidad del sistema:** Se introduce un nuevo componente (Redis) que debe ser mantenido, monitoreado y asegurado.
*   **Lógica de invalidación de caché:** La lógica de la aplicación se vuelve más compleja, ya que debe manejar tanto la escritura en la base de datos como la invalidación en la caché. Un error en la lógica de invalidación podría llevar a que se sirvan datos obsoletos.
*   **Consistencia eventual (mínima):** Existe una ventana de tiempo muy pequeña (milisegundos) entre la escritura en la base de datos y la invalidación de la caché donde una lectura podría obtener un dato obsoleto. Sin embargo, este riesgo es mínimo y aceptable para este caso de uso.

### Mitigaciones para los puntos negativos

*   **Operación de invalidación robusta:** La invalidación de la caché se implementará dentro de la misma lógica de caso de uso que la escritura, asegurando que se ejecute de manera fiable. Se pueden usar patrones como `try-catch-finally` para garantizar que la invalidación se intente incluso si ocurren otros errores.

# ADR 001: Adopción de arquitectura limpia con NestJS

## 1. Contexto

La API de Tracking debe manejar una lógica de negocio que crecerá en complejidad (reglas de transición de estado, validaciones, etc.). Además, debe ser altamente mantenible, escalable y, sobre todo, **testable** de forma aislada.

Un enfoque tradicional, donde la lógica de negocio se acopla directamente al framework web (controladores) o a la base de datos (modelos), generaría una deuda técnica insostenible y dificultaría las pruebas unitarias.

## 2. Decisión

Adoptaremos los principios de **arquitectura limpia (Clean Architecture)** para estructurar el proyecto. Usaremos **NestJS** no como un framework monolítico, sino como el "manejador" o la capa de **inyección de dependencias (DI)** que conecta las capas.

La estructura se dividirá en cuatro capas concéntricas:

1.  **Domain (Dominio):** Contiene las entidades de negocio puras (`Unit`, `Checkpoint`), la lógica de negocio (`unit.addCheckpoint()`), las reglas de la máquina de estados y las **interfaces** de los repositorios (`IUnitRepository`). No depende de nada.
2.  **Application (Aplicación):** Contiene los **Casos de Uso** (ej. `RegisterCheckpointUseCase`). Orquesta el dominio y depende *solo* de las interfaces del dominio.
3.  **Infrastructure (Infraestructura):** Implementa las interfaces definidas en el dominio (ej. `PostgresUnitRepository`). Contiene todo el código "externo": conexión a BD (TypeORM/PostgreSQL), cache (Redis), etc.
4.  **Presentation (Presentación):** La capa más externa. Para esta API, son los `Controllers` de NestJS, que manejan HTTP, validan DTOs y llaman a los Casos de Uso.

La **Regla de dependencia** será estrictamente aplicada: las dependencias solo pueden apuntar hacia adentro (Presentación -> Aplicación -> Dominio).

## 3. Consecuencias

### Positivas (+)

*   **Alta testabilidad:** El dominio y la aplicación se pueden probar unitariamente sin levantar la base de datos, el servidor web o cualquier dependencia externa.
*   **Bajo acoplamiento y alta cohesión:** La lógica de negocio (Dominio) no sabe si la base de datos es PostgreSQL o MongoDB, o si la API es HTTP o gRPC. Podemos cambiar la implementación de la base de datos (ej. migrar de TypeORM a Prisma) modificando *solo* la capa de Infraestructura, sin tocar un solo archivo de lógica de negocio.
*   **Mantenibilidad:** El código está organizado por capacidad de negocio (módulos) y por responsabilidad (capas), facilitando encontrar y modificar la lógica.

### Negativas (-)

*   **Mayor "boilerplate":** Introduce más archivos y abstracciones (Interfaces, DTOs, Mapeadores) que un enfoque simple de MVC. Es una inversión inicial en estructura.
*   **Curva de aprendizaje:** El equipo debe entender y respetar la Regla de Dependencia y el flujo de control (ej. cómo un `Controller` llama a un `UseCase` que usa una `Interface` que implementa un `Repository`).

# ADR 002: Cola de mensajes

## 1. Contexto

El requisito funcional más crítico es: **"Se debe garantizar que todos los checkpoints (cambios de estado) sean aplicados"**.

El sistema enfrenta picos de escritura significativos (~120.000 unidades en 2 horas). Un enfoque **síncrono**, donde el endpoint `POST /checkpoints` escribe directamente en la base de datos, es frágil:

1. **Pérdida de datos:** Si la base de datos está caída o lenta, la petición HTTP falla, y el escaneo (checkpoint) se pierde para siempre, a menos que el dispositivo cliente tenga una lógica de reintento compleja.
2. **Baja disponibilidad:** La API se vuelve lenta, atada al rendimiento de la escritura de la base de datos.
3. **Mal manejo de picos:** Un pico de escaneos puede saturar la base de datos y tumbar todo el sistema.

## 2. Decisión

Se implementará el patrón **Productor-Consumidor** usando una cola de mensajes (**RabbitMQ**) para desacoplar la ingesta de checkpoints del procesamiento.

El flujo será el siguiente:

1. **Productor (API):** El endpoint `POST /api/v1/checkpoints` se vuelve extremadamente ligero. Su *única* responsabilidad es validar el DTO de entrada y publicar el mensaje del checkpoint en una cola de RabbitMQ.
2. **Respuesta inmediata:** La API responde inmediatamente con `202 Accepted` (Aceptado para procesamiento), dando una experiencia de usuario (operador) instantánea.
3. **Consumidor (Worker):** Un proceso NestJS separado (`main.worker.ts`) actuará como consumidor. Escuchará la cola, recibirá los mensajes uno por uno y ejecutará el `RegisterCheckpointUseCase` (que aplica la lógica de dominio y escribe en la BD).

Para cumplir con la "garantía de entrega", se usará un patrón de **Dead Letter Queue (DLQ)**. Si un mensaje falla repetidamente en el worker (debido a un bug o datos corruptos), no se descarta; se mueve a una cola "muerta" para análisis manual, asegurando que **ningún evento se pierda**.

## 3. Consecuencias

### Positivas (+)

* **Garantía de entrega y resiliencia:** Si la base de datos falla, los checkpoints no se pierden. Simplemente esperan en la cola y el worker los procesará cuando la BD se recupere.
* **Alta disponibilidad (API):** El endpoint de ingesta (`POST /checkpoints`) es ahora ultra-rápido (< 50ms) y casi nunca fallará, ya que su única dependencia (RabbitMQ) está diseñada para ingesta de alta velocidad.
* **Manejo de picos (Throttling):** La cola actúa como un *buffer* (amortiguador). Un pico de 10.000 escaneos se absorbe instantáneamente, y el worker los procesa a un ritmo constante que la base de datos puede soportar cómodamente.

### Negativas (-)

* **Consistencia eventual:** Esta es la principal contrapartida. Cuando la API responde `202 Accepted`, el checkpoint *aún no está* en la base de datos. Si un cliente consulta `GET /tracking/:id` un segundo después, verá el estado *anterior*. El sistema se vuelve "eventualmente consistente" (generalmente en < 1 segundo, pero no es instantáneo).
* **Mayor complejidad operativa:** Se introduce un nuevo componente crítico en el sistema (RabbitMQ) que debe ser monitoreado y mantenido.
* **Dos puntos de entrada:** La aplicación ahora tiene dos procesos en ejecución: la API (Productor) y el Worker (Consumidor).

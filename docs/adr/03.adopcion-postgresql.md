# ADR 003: Adopción de base de datos relacional con PostgreSQL

**Estado:** Aceptado
**Fecha:** 2025-11-18

## 1. Contexto

El sistema de tracking requiere una base de datos que garantice la máxima **fiabilidad e integridad de los datos**. Las operaciones deben ser transaccionales para asegurar la consistencia (ACID). Además, el negocio necesita la capacidad de realizar **consultas complejas y análisis avanzados** sobre los datos de seguimiento para obtener inteligencia de negocio y optimizar la operativa.

## 2. Decisión

Se utilizará **PostgreSQL** como la base de datos principal para el sistema.

El modelo de datos se basará en un esquema relacional clásico:
*   Una tabla `units` para almacenar la información de cada paquete (guía, estado actual, etc.).
*   Una tabla `checkpoints` para registrar cada evento de tracking, con una clave foránea (`foreign key`) que la relaciona con la tabla `units`.

Se crearán índices en las columnas de consulta frecuente, como `tracking_id` en la tabla `units` y la columna de la clave foránea en `checkpoints`, para asegurar un rendimiento óptimo.

## 3. Consecuencias

### Positivas (+)

*   **Integridad de datos y consistencia (ACID):** PostgreSQL ofrece garantías transaccionales completas, asegurando que cada operación se complete de manera atómica y fiable, previniendo estados de datos corruptos.
*   **Flexibilidad para consultas avanzadas:** El lenguaje SQL permite realizar consultas complejas, agregaciones y `JOINs` que son fundamentales para la reportería operativa y la inteligencia de negocio.
*   **Modelo de datos relacional maduro:** Un esquema relacional previene la duplicación de datos y asegura la integridad referencial mediante claves foráneas, resultando en un modelo robusto y probado.
*   **Ecosistema y herramientas:** PostgreSQL cuenta con un ecosistema muy maduro de herramientas para administración, respaldo, replicación y optimización.

### Negativas (-)

*   **Rendimiento en lecturas de historial:** La consulta del historial completo de un paquete (`GET /tracking/:trackingId`) requiere un `JOIN`, que puede ser una operación más intensiva que una simple lectura de documento.

### Mitigaciones para los puntos negativos

*   **Capa de caché con Redis:** Para mitigar el impacto de los `JOINs` en las consultas frecuentes, se implementa una capa de caché con Redis (ver ADR 004), reduciendo drásticamente la carga sobre PostgreSQL.
*   **Indexación estratégica:** Se aplicará una estrategia de indexación cuidadosa en las claves primarias, foráneas y columnas de búsqueda para acelerar las consultas.
*   **Particionamiento de tablas:** A futuro, si el volumen de datos crece exponencialmente, PostgreSQL ofrece técnicas avanzadas como el particionamiento de tablas para mantener el rendimiento.

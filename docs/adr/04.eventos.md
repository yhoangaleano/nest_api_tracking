# ADR 004: Manejo de eventos

## 1. Contexto

Al adoptar una cola de mensajes (ADR 002), perdemos la garantía de procesamiento secuencial estricto. En un sistema distribuido, es posible que el checkpoint `IN_TRANSIT` (Mensaje B) llegue a la cola *antes* que el checkpoint `PICKED_UP` (Mensaje A), debido a latencia de red del dispositivo de escaneo o reintentos.

Si procesamos el Mensaje B primero, el sistema registraría un estado incoherente. No podemos depender únicamente de la hora del *timestamp* para ordenar, ya que el mensaje de "orden" (Mensaje A) aún no ha sido procesado.

## 2. Decisión

La responsabilidad de garantizar la secuencialidad de los estados recaerá en la **Capa de Dominio**, específicamente dentro de la entidad `Unit.entity.ts`.

1. **Máquina de estados:** La entidad `Unit` implementará un método privado `canTransitionTo(newState)` que contiene una máquina de estados finitos (FSM). Esta FSM define las transiciones válidas (ej. `CREATED` -> `PICKED_UP`; `PICKED_UP` -> `IN_TRANSIT`).

2. **Lógica de negocio:** El método `unit.addCheckpoint(checkpoint)` validará la transición usando la FSM *antes* de añadir el checkpoint.
    * Si la transición es **válida**, se aplica el estado.
    * Si la transición es **inválida** (ej. estado actual `CREATED`, nuevo estado `IN_TRANSIT`), el método lanzará un error de dominio específico: `InvalidStateTransitionError`.

3. **Lógica del worker (consumidor):** El worker de RabbitMQ (`checkpoint-consumer.ts`) será el encargado de manejar este error:
    * `try { await useCase.execute(...) }`
    * `catch (error)`:
        * Si el error es `InvalidStateTransitionError`: Esto significa que el mensaje llegó fuera de orden. El worker **hará un NACK** (Not Acknowledged) del mensaje y le pedirá a RabbitMQ que lo **vuelva a encolar con un retraso** (ej. 10 segundos).
        * Si es cualquier otro error: El mensaje se envía a la **Dead Letter Queue (DLQ)** (ADR 002).

Este re-encolado le da tiempo al mensaje faltante (Mensaje A) de ser procesado, y en el reintento, el Mensaje B encontrará la entidad en un estado válido (`PICKED_UP`) y será procesado con éxito.

## 3. Consecuencias

### Positivas (+)

* **Consistencia de datos garantizada:** El sistema se auto-corrige. Es imposible que la base de datos termine en un estado ilógico.
* **Lógica de negocio centralizada:** La regla de negocio (la máquina de estados) vive en un solo lugar (`Unit.entity.ts`), cumpliendo con los principios de Arquitectura Limpia (ADR 001) y facilitando su modificación.
* **Resiliencia:** El sistema es robusto frente a problemas de red o latencia en el envío de eventos.

### Negativas (-)

* **Complejidad del worker:** El consumidor de la cola se vuelve más inteligente (y complejo), ya que debe diferenciar entre "errores fatales" (a DLQ) y "errores transitorios" (re-encolar).
* **Latencia de procesamiento:** Un mensaje fuera de orden *retrasará* su propio procesamiento (ej. 10 segundos), pero esto es preferible a corromper los datos.

# ADR 003: Modelo NoSQL (MongoDB) con array embebido

## 1. Contexto

El rendimiento del sistema tiene dos vertientes: la ingesta de *escritura* (resuelta en ADR 002) y la *lectura*. La consulta más frecuente y crítica para el cliente será `GET /api/v1/tracking/:trackingId`, que debe devolver el estado actual y el historial completo de un paquete.

En un modelo relacional (SQL), esto requeriría dos tablas (`units` y `checkpoints`) y un `JOIN` para cada consulta de tracking. Dado el volumen de checkpoints (~1.21M/día), la tabla de `checkpoints` crecería rápidamente, y este `JOIN` podría convertirse en un cuello de botella.

## 2. Decisión

Se utilizará una base de datos NoSQL documental, **MongoDB**, como almacén de datos principal.

La decisión de modelado clave es **embeber los checkpoints como un array dentro del documento de la unidad (`Unit`)**. En lugar de tener una colección de `units` y otra de `checkpoints`, tendremos una sola colección `units`.

El esquema del documento será:

```json
{
  "_id": "unit-id-123",
  "trackingId": "T-ABC-123", // Indexado (unique)
  "guideId": "guide-id-789",
  "currentState": "IN_TRANSIT", // Indexado (para GET /shipments)
  "checkpoints": [
    {
      "status": "CREATED",
      "timestamp": "2025-11-08T10:00:00Z",
      "location": "Warehouse A",
      "notes": "..."
    },
    {
      "status": "PICKED_UP",
      "timestamp": "2025-11-08T14:30:00Z",
      "location": "Warehouse A"
    },
    {
      "status": "IN_TRANSIT",
      "timestamp": "2025-11-08T18:00:00Z",
      "location": "On route to B"
    }
  ]
}
```

## 3. Consecuencias

### Positivas (+)

* **Lecturas de tracking instantáneas:** La consulta `GET /tracking/:trackingId` se traduce en un `findOne({ trackingId: "..." })`. Esta operación (sobre un índice) es la más rápida que MongoDB puede ejecutar. Devuelve el documento completo (unidad + historial) en una sola operación de E/S, eliminando la necesidad de JOINs.
* **Atomicidad de escritura:** Añadir un nuevo checkpoint (ADR 002) es una operación atómica y eficiente (`$push` al array `checkpoints` y un `$set` al campo `currentState`).
* **Consulta de estado eficiente:** La consulta `GET /shipments?status=...` se resuelve con un `find({ currentState: "..." })`, que es rápido gracias al índice en `currentState`.

### Negativas (-)

* **Tamaño del documento:** El límite de un documento en MongoDB es de 16MB. Aunque el contexto (ciclo de 3 días, 10 checkpoints/unidad) indica que no nos acercaremos a este límite, es una restricción a monitorear si el ciclo de vida de los paquetes se alarga. O validar una posible migracion de estos datos historicos a un lago o otro lugar para evitar crecer indefinidamente.
* **Menor flexibilidad analítica:** Las consultas de agregación complejas (ej. "¿cuántos paquetes pasaron por la bodega A y B el lunes?") son más difíciles de realizar que en SQL. Sin embargo, dado que el foco principal es la consulta rápida de tracking, este trade-off es aceptable.

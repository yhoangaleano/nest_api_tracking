# ADR 005: Política de no-caché para lecturas de tracking individual

**Estado:** Aceptado
**Fecha:** 2025-11-12

## 1. Contexto

Una estrategia común para optimizar el rendimiento de lectura en APIs de alto tráfico es introducir una capa de caché (como **Redis**) para servir las peticiones `GET` frecuentes y aliviar la carga de la base de datos principal.

Se evaluó el uso de Redis para el endpoint `GET /api/v1/tracking/:trackingId`.

## 2. Decisión

Se ha decidido **NO implementar** una capa de caché (como Redis o Memcached) para el endpoint de consulta de tracking individual (`GET /tracking/:trackingId`).

Las consultas de este endpoint golpearán directamente la base de datos MongoDB.

## 3. Justificación (Consecuencias)

La decisión se basa en que los inconvenientes superan a los beneficios para este caso de uso específico.

### Inconvenientes de implementar caché (por qué NO)

1. **Datos obsoletos (staleness):** El requisito funcional más importante de una API de tracking es la **confianza**. Si usamos un caché basado en TTL (Time-to-Live), un cliente podría consultar un paquete y verlo como `OUT_FOR_DELIVERY`, aunque el paquete haya sido escaneado como `DELIVERED` 5 segundos antes. Esta inconsistencia es funcionalmente inaceptable.

2. **Complejidad de invalidación:** Para evitar datos obsoletos, tendríamos que implementar una invalidación de caché explícita (cache invalidation). Esto requeriría que el Worker (ADR 002) publique un segundo evento ("invalidar-cache-T-123") después de escribir en la BD, añadiendo una enorme complejidad, otro punto de fallo y latencia al sistema.

### Beneficios inexistentes (por qué NO es necesario)

1. **La lectura ya es instantánea:** Gracias al modelo de datos de MongoDB (ADR 003), la consulta `findOne({ trackingId: "..." })` sobre un campo indexado es una operación `O(1)` (en términos prácticos) que la base de datos resuelve en **sub-milisegundos**. La base de datos en sí misma ya actúa como un caché de memoria/disco para esto. No hay un `JOIN` costoso o una agregación que optimizar.

2. **Carga de lectura manejable:** La carga de lectura para consultas individuales por `trackingId` (que son operaciones de búsqueda por clave) es fácilmente manejable por un clúster de MongoDB moderno.

---
**Nota aclaratoria:** Esta decisión *no* prohíbe el uso de caché para *otros* endpoints. Por ejemplo, un endpoint analítico (ej. `GET /api/v1/dashboard/stats`) que ejecute agregaciones costosas (`$group` y `$count`) **SÍ** sería un candidato ideal para un caché con TTL, ya que la analítica puede tolerar un ligero retraso.

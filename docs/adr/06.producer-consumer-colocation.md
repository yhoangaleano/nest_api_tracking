# ADR 006: Productor y consumidor en mismo servicio

## 1. Contexto

Siguiendo la ADR 002, que estableció el patrón Productor-Consumidor usando RabbitMQ, necesitamos decidir sobre la arquitectura de despliegue:

**Opción 1: Microservicios separados**

- Servicio API (solo Productor) - maneja peticiones HTTP, publica en la cola
- Servicio worker (solo Consumidor) - procesa mensajes de la cola

**Opción 2: Servicio unificado**

- Servicio único - tanto productor como consumidor en la misma aplicación NestJS
- Infraestructura, dependencias y código compartidos

## 2. Decisión

Se **ubicarán tanto el Productor como el Consumidor en el mismo servicio NestJS** para la fase inicial de MVP y primeras etapas de producción.

### Justificación

**Optimización de costos de infraestructura**

- Servicios separados requieren:
  - 2+ contenedores/instancias (API + Worker)
  - Configuraciones de escalado separadas
  - Load balancers adicionales
  - Mayor complejidad de monitoreo
- Un solo servicio reduce costos de infraestructura en ~40-50% en etapas tempranas

**Velocidad y simplicidad del MVP**

- Despliegue e iteración más rápidos
- Un solo código base para mantener
- Pipeline de CI/CD más simple
- Debugging y logging más fáciles (un solo proceso)

**Proyecciones de volumen actual**

- Carga esperada: ~120,000 unidades en 2 horas (16-17 mensajes/segundo promedio)
- Pico de carga: ~50-100 mensajes/segundo
- Este volumen está bien dentro de la capacidad de un solo servicio con configuración apropiada

**Simplicidad operacional**

- Un solo proceso para monitorear
- Pools de conexión compartidos (MongoDB, RabbitMQ)
- Tracking de errores y logging simplificados

## 3. Detalles de arquitectura

### Implementación actual

```
┌─────────────────────────────────────┐
│  Servicio NestJS (Puerto 3000)      │
│                                     │
│  ┌──────────────┐  ┌──────────────┐│
│  │   Productor  │  │  Consumidor  ││
│  │  (HTTP API)  │  │  (Worker)    ││
│  └──────┬───────┘  └──────┬───────┘│
│         │                 │         │
└─────────┼─────────────────┼─────────┘
          │                 │
          ▼                 ▼
    ┌──────────────────────────┐
    │    Cola RabbitMQ         │
    │  - checkpoint_events     │
    │  - checkpoint_events_dlq │
    └──────────────────────────┘
```

### Configuración clave

- Prefetch del consumidor: 10 mensajes (procesamiento concurrente)
- Cola de delay para backoff de reintentos (sin bloqueo de setTimeout)
- Conexión compartida de RabbitMQ entre productor y consumidor

## 4. Consecuencias

### Positivas (+)

* **Menores costos:** Un solo contenedor/instancia para ejecutar y mantener

* **Entrega más rápida del MVP:** Arquitectura más simple acelera el desarrollo

* **Recursos compartidos:** Un solo pool de conexiones para MongoDB y RabbitMQ

* **Debugging más fácil:** Todos los logs en un lugar, un solo proceso para debuggear

* **Rendimiento suficiente:** Las proyecciones de carga actuales están bien dentro de la capacidad


### Negativas (-)

* **No se puede escalar independientemente:** Si el consumidor necesita más recursos, se debe escalar todo el servicio

* **Punto único de falla:** Si el servicio cae, tanto API como worker están caídos

* **Competencia de recursos:** Productor y consumidor comparten CPU/memoria

* **Menos flexible:** No se puede optimizar cada componente por separado (ej: instancias optimizadas para consumidor)

## 5. Ruta de migración

Cuando se cumplan las siguientes condiciones, se debe **separar en servicios distintos**:

### Disparadores para la separación

1. **Umbral de volumen:** Carga sostenida > 500 mensajes/segundo
2. **Profundidad de cola:** Profundidad regular de cola > 5,000 mensajes
3. **Lag del consumidor:** Lag de procesamiento regular > 5 minutos
4. **Contención de recursos:** Productor y consumidor compitiendo por recursos
5. **Criticidad del negocio:** La disponibilidad de la API se vuelve más crítica que la velocidad de procesamiento

### Estrategia de migración

```
Fase 1: Actual (coubicado)
└── Servicio NestJS único con productor y consumidor

Fase 2: Separación gradual (cuando se cumplan los disparadores)
├── Servicio API (Productor)
│   └── Solo endpoints HTTP
└── Servicio Worker (Consumidor)
    └── Solo procesamiento de cola

Fase 3: Escalado horizontal (si es necesario)
├── Servicio API (Productor) - 2+ instancias
└── Servicio Worker (Consumidor) - 3+ instancias
```

## 6. Alertas de monitoreo

Para detectar cuándo es necesaria la separación, monitoreamos:

**Métricas de cola**

- ⚠️ Profundidad de cola > 1,000 mensajes (advertencia)
- 🚨 Profundidad de cola > 5,000 mensajes (crítico)

**Rendimiento del consumidor**

- ⚠️ Lag del consumidor > 2 minutos (advertencia)
- 🚨 Lag del consumidor > 5 minutos (crítico)

**Métricas de procesamiento**

- ⚠️ Tiempo promedio de procesamiento > 500ms (advertencia)
- ⚠️ Tasa de reintentos > 10% (advertencia)
- 🚨 Mensajes en DLQ > 100 (crítico)

**Utilización de recursos**

- ⚠️ CPU > 70% sostenido (advertencia)
- ⚠️ Memoria > 80% sostenida (advertencia)

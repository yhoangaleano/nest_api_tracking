# ADR 002: Adopción de procesamiento síncrono para checkpoints

**Estado:** Aceptado
**Fecha:** 2025-11-18

## 1. Contexto

El proceso de registro de checkpoints es una operación crítica que requiere **retroalimentación inmediata y fiable** al operador. Para garantizar la integridad operativa, es fundamental que el sistema confirme el éxito o fracaso de cada registro en tiempo real. Una respuesta diferida (como un `202 Accepted`) introduce incertidumbre y no permite corregir errores en el momento, afectando la fiabilidad de la cadena de seguimiento.

## 2. Decisión

Se implementa un **procesamiento síncrono** para el registro de checkpoints. El endpoint `POST /api/v1/checkpoints` ejecuta toda la lógica de negocio y persiste los datos en la base de datos dentro del ciclo de la misma petición HTTP.

El flujo de trabajo es el siguiente:
1.  **Recepción y validación:** El controlador recibe la petición y valida el DTO de entrada.
2.  **Ejecución del caso de uso:** Se invoca el `RegisterCheckpointUseCase`, que orquesta la lógica de dominio.
3.  **Validación de dominio:** La entidad de negocio valida la transición de estado según la máquina de estados definida.
4.  **Persistencia:** Si la transición es válida, los datos se guardan en la base de datos PostgreSQL.
5.  **Respuesta al cliente:** La API responde con un `201 Created` si la operación fue exitosa, o un código de error (`4xx` o `5xx`) si falló.

Esta decisión se complementa con el uso de **Redis como capa de caché** (ver ADR 004) para optimizar las operaciones de lectura.

## 3. Consecuencias

### Positivas (+)

*   **Consistencia inmediata y confianza operativa:** El operador recibe una respuesta real sobre el éxito o fracaso del registro. Un `201` garantiza que el dato está en la base de datos.
*   **Simplicidad arquitectónica:** La arquitectura se mantiene simple y fácil de entender, sin la sobrecarga de componentes como brokers de mensajes o workers separados.
*   **Facilidad de depuración:** El flujo lineal de las peticiones simplifica la traza y resolución de problemas.
*   **Menor costo de infraestructura:** Se requieren menos componentes para desplegar y mantener.

### Negativas (-)

*   **Acoplamiento temporal a la base de datos:** La disponibilidad del endpoint de escritura está directamente ligada a la disponibilidad y rendimiento de la base de datos.
*   **Menor capacidad de absorción de picos:** La carga de peticiones se transfiere directamente a la base de datos, sin un buffer intermedio.

### Mitigaciones para los puntos negativos

*   **Base de datos robusta y optimizada:** El uso de PostgreSQL con índices bien definidos en las columnas críticas (`tracking_id`, `current_state`) asegura un rendimiento de escritura eficiente.
*   **Pool de conexiones:** El framework (a través de TypeORM) gestiona un pool de conexiones a la base de datos para manejar la concurrencia de manera eficaz.
*   **Escalado horizontal:** La API puede escalarse horizontalmente detrás de un balanceador de carga para distribuir las peticiones.
*   **Uso de transacciones:** Las operaciones de escritura se envuelven en transacciones de base de datos para garantizar la atomicidad y consistencia (ACID).

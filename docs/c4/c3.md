# C3: Diagrama de componentes (API web)

**Estado:** Aceptado
**Fecha:** 2025-11-12

## 1. Descripción

Este diagrama de nivel 3 (componentes) detalla la estructura interna del contenedor `API web (productor)`.

Muestra los componentes principales dentro de la aplicación NestJS y cómo orquestan el flujo de peticiones, aplicando los principios de Arquitectura Limpia (ADR 001). Se enfoca en la separación de responsabilidades:

* **Presentation (controlador):** Recibe HTTP.
* **Application (casos de uso):** Orquesta la lógica.
* **Infrastructure (repositorio, productor):** Interactúa con el exterior.

## 2. Diagrama

```mermaid
%%{ init : { "theme" : "default" } }%%
C4Component
    title "Diagrama de componentes (C3) de la API web"

    %% Actores externos (personas)
    Person(operador, "Operador logístico", "Escanea paquetes")
    Person(cliente, "Cliente", "Consulta su envío")
    Person(admin, "Administrador (backoffice)", "Monitorea la operación")

    %% Contenedores externos (con los que interactúa)
    ContainerQueue(queue, "Cola de mensajes", "RabbitMQ", "Buffer de checkpoints (ADR 002)")
    ContainerDb(db, "Base de datos", "MongoDB", "Almacén de unidades (ADR 003)")

    %% Límite del contenedor API web
    System_Boundary(api, "API web (productor)") {

        %% Componentes de Presentation (capa de entrada)
        Component(controller, "Tracking controller", "NestJS Controller", "Maneja rutas, valida DTOs y llama a casos de uso")
        Component(auth_mw, "Auth middleware", "NestJS Middleware/Guard", "Valida JWT y permisos")

        %% Componentes de Application (casos de uso)
        Component(get_tracking_uc, "GetTrackingHistory use case", "NestJS Service", "Lógica para obtener historial")
        Component(list_units_uc, "ListUnitsByState use case", "NestJS Service", "Lógica para listar unidades")

        %% Componentes de Infrastructure (adaptadores)
        Component(queue_producer, "Checkpoint producer", "NestJS Service", "Implementación para publicar en RabbitMQ")
        Component(repo_interface, "IUnitRepository", "TypeScript Interface", "Abstracción del repositorio (ADR 001)")
    }

    %% --- Relaciones externas ---
    Rel(operador, auth_mw, "POST /checkpoints")
    Rel(cliente, auth_mw, "GET /tracking/:id")
    Rel(admin, auth_mw, "GET /shipments")

    %% --- Relaciones internas (flujo) ---

    %% Flujo de autenticación
    Rel(auth_mw, controller, "Pasa petición autenticada")

    %% Flujo de escritura (asíncrono)
    Rel(controller, queue_producer, "Usa", "1. Llama al productor (escritura)")
    Rel(queue_producer, queue, "Publica mensaje", "AMQP")

    %% Flujo de lectura (síncrono)
    Rel(controller, get_tracking_uc, "Usa", "2. Llama al caso de uso (lectura)")
    Rel(controller, list_units_uc, "Usa", "3. Llama al caso de uso (lectura)")

    Rel(get_tracking_uc, repo_interface, "Depende de")
    Rel(list_units_uc, repo_interface, "Depende de")

    %% --- Relaciones de implementación ---
    %% Esta relación es clave: el repo_interface es implementado por la BD
    %% (aunque la implementación real está en el worker, la API la usa para leer)
    Rel(db, repo_interface, "Implementa (para lecturas)", "Mongoose (findOne)")
```
